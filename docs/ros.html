Four checks for headless ROS jobs on shared compute nodes: the code that runs, network isolation, reliable startup and complete output.

Before you start

Keep the project’s ROS setup.

ROS jobs on Aqua run headless on shared compute nodes. Most problems come from running different code, or sharing a network, without realising it.

  • Keep your project’s ROS distribution, middleware and environment. Read package.xml, launch files, Pixi tasks and setup scripts before changing anything.
  • Don’t assume /opt/ros/humble exists on Aqua. Source the intended underlay and overlay inside the job.
  • Keep heavy builds off the login node.
Check 1

Confirm the code that actually runs.

Editing src/ does not always update an installed copy. New entry points, packaging changes and compiled code need a rebuild. Record what the job resolves in its log:

Inside the job, after activating the environment · replace the names 
ros2 pkg prefix YOUR_PACKAGE
python3 -c "import YOUR_MODULE; print(YOUR_MODULE.__file__)"
printenv | grep -E '^(ROS_|RMW_)' | sort

These commands only read. The last line shows ROS and middleware settings after activation, which is what the nodes really use.

Check 2

Keep jobs from hearing each other.

Jobs sharing a node can discover each other’s ROS participants. Give each job its own discovery setup:

  • Allocate ROS domain IDs deliberately. A hash of the job ID can collide, and very many processes in one domain can still run out of ports.
  • For single-node jobs, localhost-only discovery can help, but other jobs on the same host still share localhost. Verify the isolation you get.
  • Check the settings after Pixi or container activation. Activation can override variables passed by PBS, so the scheduler record shows what you asked for, not what the nodes used.
Check 3

Start reliably, stop cleanly.

  • Wait for subscribers to confirm they are ready before playing bags. A short-lived ready signal can vanish before a slow model finishes loading.
  • Use startup and inactivity timeouts so a stuck pipeline ends instead of burning walltime.
  • Pass child-process errors up, track the processes the run starts, and clean up only those.
Check 4

Prove every sensor produced output.

  • Save bag timestamps, clock source, playback rate, QoS and topic remappings with the run configuration.
  • Count expected messages or results per sensor. A run that exits cleanly can still have skipped data.
  • If transport seems broken, test a minimal publisher/subscriber pair inside the same allocation before blaming the middleware.
Using an AI agent?

Ask for these checks up front.

With the aqua-hpc skill installed, the agent already knows these checks. Ask for a smoke case first:

Agent prompt · fill in your own launch file and bags 
Run these bags headlessly on Aqua with the existing launch file [launch],
varying [sensor configuration] and [model]. Before scaling, verify the overlay
paths that actually run, the effective ROS domain and discovery settings,
readiness before playback, and message coverage per sensor.
Prepare one smoke case first; do not submit the full set yet.
